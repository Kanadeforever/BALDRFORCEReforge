## 2. 目标程序与版本关系

- BFE：`BaldrForce.exe`，2003 原版，32 位 x86；
- BFSE：`BaldrForceSE.exe`，Standard Edition，32 位 x86；
- 两版高度同源，但属于不同构建，**不能直接照搬 SE 绝对地址**；
- 正式 ASI 目标只针对已经逆向确认的 BFE 原版 EXE。

PE 默认 ImageBase：

```text
0x00400000
```

源码保存 RVA，运行时按：

```text
实际 EXE 基址 + RVA
```

取地址。

## 3. BFSE 新增剧情语音的资源结构

BFE 原版主要有：

```text
Voice1.pac
Voice2.pac
```

BFSE 追加：

```text
Voice3.pac
```

用户已用 GARbro 确认 `Voice3.pac` 就是主角追加剧情语音资源，里面存在：

```text

...

```

`Voice2` 两版文件数量一致，所以剧情新增资源的关键差异是 `Voice3.pac`。

本包不分发商业资源；使用者必须从自己的 BFSE 安装取得 `Voice3.pac`。

## 4. 剧情脚本与 @v 结论

脚本文本记录基本结构确认：

```text
0B 00
uint32 little-endian 字符串长度
CP932 字符串
00
```

BFSE 并没有为主角剧情语音新增独立二进制 opcode，而是在现有文本开头直接加入控制标签。

典型对比：

```text
BFE：
@f1A0101「……ああ聞いているよ、月菜」

BFSE：
@v500000@f1A0101「……ああ聞いているよ、月菜」
```

序章特殊独白：

```text
@h00@vTR0001
...
@h00@vTR0007
```

因此总体路线不是自己播放 WAV，而是让 BFE 继续走原生 `@v` 系统。

## 5. 为什么不重写 BIN

用户的旧汉化已经修改过 BFE BIN。再次反编译/重编译存在：

- 跳转/指针重算风险；
- BFET 尾部结构被破坏风险；
- 与旧汉化正文冲突；
- 不同版本脚本结构错位；
- 回滚与分发复杂度增加。

同引擎历史工具也出现过 Baldr Force 脚本 pointer fix 问题。

最终路线固定：

```text
离线确定位置
-> ASI 运行时识别
-> 只改已经复制出来的临时字符串
```

磁盘 BIN 永远不写。

## 6. BFE/BFSE 脚本总体差异

已确认：

- BFE BIN：301 个；
- BFSE BIN：280 个；
- 忽略大小写共同脚本：279 个；
- BFE 独有：22 个（包括 `after.bin`、`Replay21`～`Replay41`）；
- BFSE 独有：`ren01b.bin`；
- BFSE 有若干极小占位 BIN，没有可提取正常文本记录。

不能用“BFSE 第 N 句 = BFE 第 N 句”直接迁移，因为 SE 有全年龄改写、演出调整和局部结构变动。

离线映射曾综合：

- 文本相似度；
- 前后文；
- 局部序列；
- 锚点；
- 人工正/负样本。

允许连续上下文中的改写，不允许只因孤立短句相似就强行配对。

## 8. 旧汉化 BFET 兼容原理

旧汉化会把 BFET 数据追加到真正执行流之后。

BIN 头确认：

```text
stream_start = 16 + (u32@0x08 * 4)
stream_size  = u32@0x0C
```

例如序章汉化文件总长度会增长，但真正执行流长度保持原来的范围。

所以正式身份键只使用：

```text
FNV-1a32(真正执行流)
+
0x000B 记录相对执行流偏移
```

不哈希整个文件，也不比较最终中文正文。

## 9. 正式剧情运行时地址

### 9.1 0x0B 文本复制

```text
CALL site：VA 0x004AB5D2 / RVA 0x000AB5D2
原复制函数：VA 0x004ACC20 / RVA 0x000ACC20
```

运行时状态已确认字段：

```text
state + 0x0C  = 脚本执行流长度
state + 0x114 = 当前读取游标
state + 0x128 = 脚本执行流基址
```

CALL 发生时 opcode 和 4 字节长度已被读取，因此：

```text
recordOffset = cursorBeforeCopy - 6
```

临时文本槽：

```text
destination - 8 : opcode DWORD
destination - 4 : 字符串长度，含 NUL
destination     : 文本本体
```

临时槽容量约：

```text
0x1000 bytes
```

正式版在容量不足或结构校验不符时直接不注入，绝不越界。

### 9.2 PAC 挂载

```text
CALL site：VA 0x004612BB / RVA 0x000612BB
原 PAC 打开函数：VA 0x004AE330 / RVA 0x000AE330
```

原版成功打开 `Voice2.pac` 后，用同一个 PAC manager `self` 再打开：

```text
Voice3.pac
```

返回给原游戏的仍然是原 `Voice2.pac` 请求结果；即使没有 `Voice3.pac`，也不把原资源初始化改成失败。

### 9.3 TRxxxx 兼容

```text
@v 参数入口：VA 0x0049EA40 / RVA 0x0009EA40
数字原版继续：VA 0x0049EA46 / RVA 0x0009EA46
TR 跳回播放流程：VA 0x0049EAF9 / RVA 0x0009EAF9
```

BFE 原版只解析十进制数字。test1 直接注入 `@h00@vTR0001` 时：

- `@h00` 原版不认识；
- `TR` 也不符合数字参数；
- 屏幕出现 `00TR0001`；
- 没有 TR 音频。

test2 起固定方案：

- 文本只注入 `@vTR0001`；
- 只在 `0x0049EA40` 接管 `TR`；
- 复制 6 字节资源键；
- 追加 `.wav`；
- 同步维护 `this+0x60` 的当前语音文件名；
- 跳过不适用于主角 TR 独白的旧角色可用性检查；
- 模式、忙碌、声音播放与 Backlog 后续仍走原版。

### 12.7 BattleVoiceSelect BFE/BFSE 对比

BFE selector：

```text
VA 0x004559A0
```

BFSE 对应 selector：

```text
VA 0x00458250
```

全局 CALL 统计：

```text
BFE  -> 9 个调用点
BFSE -> 10 个调用点
```

原有 9 个可以对应。BFSE 唯一多出的入口在：

```text

```

其核心调用：

```asm

push esi

```

即：

```text

```

BFE 同源位置约：

```text

```

没有这条调用。

category 0 对应 `tooru.dat` 前 4 个槽：

```text

slot 1 tooru0102A.wav
slot 2 tooru0103B.wav
slot 3 tooru0104A.wav
```

## 14. 正式源码架构

`BaldrForceVoiceSE.cpp` 现在只剩三条核心 Hook：

1. **Script CALL Hook**
   - 识别安全 VoiceMap；
   - 调原字符串复制；
   - 在临时文本前插 `@v`。

2. **PAC Open CALL Hook**
   - 原请求先照常执行；
   - Voice2 成功后追加 Voice3。

3. **TR @v parser Hook**
   - 只接管 `TRxxxx`；
   - 数字型 VoiceTag 立即回原版。

没有任何战斗 Hook、文件日志 API、CSV writer 或运行时审计数组。
