## 2. 项目目标

让 2003 原版《BALDR FORCE EXE》（BFE）播放《BALDR FORCE Standard Edition》（BFSE）后来追加的**主角剧情语音**。

实现路线固定为「离线定位 + 运行时内存改写」：

- 不修改任何 .bin；
- 不重新打包 Chapter.pac；
- 不自己播放 WAV；
- 不自己实现 PAC 读取器；
- 尽量让原游戏自己的资源系统、@v 控制码解释器和声音系统完成工作。

由此得到的硬性设计约束：运行时只能依赖与「正文内容」无关的身份键，才能同时兼容原始日文 BIN 与旧汉化 BIN。

## 3. 目标程序与基线

- BFE：BaldrForce.exe，2003 原版，32 位 x86；
- BFSE：BaldrForceSE.exe，Standard Edition，32 位 x86；
- 两版高度同源，但属于不同构建，**不能直接照搬 SE 的绝对地址**；正式 ASI 只针对已经逆向确认的 BFE 原版 EXE；
- 是否支持其它版本/其它语言版 EXE：**待确认**（本插件在机器码校验不符时会安静地拒绝打补丁，而不是盲写）。

PE 默认 ImageBase：

```text
0x00400000
```

源码保存的是 RVA，运行时按「实际 EXE 基址 + RVA」取地址，因此主 EXE 被系统搬到其它基址时仍然成立。

当前目录规范（2026-09-25 重组后）：

```text

release                目录：所有编译产物，固定在项目根（不再放在模块内）
```

## 4. 逆向结论

### 4.1 语音资源结构

BFE 原版主要有：

```text
Voice1.pac
Voice2.pac
```

BFSE 追加：

```text
Voice3.pac
```

用户已用 GARbro 确认 Voice3.pac 就是主角追加剧情语音资源，里面存在 500000.wav … TR0001.wav 等条目。Voice2 两版文件数量一致，所以剧情新增资源的关键差异是 Voice3.pac。

BFSE 主角剧情语音的主要 VoiceTag 前缀：

```text
5xxxxx
6xxxxx
7xxxxx
TRxxxx
```

非 Replay 主线发现约 5916 个唯一主角 VoiceTag（**待确认**：该数值来自重组前的离线研究记录，本轮未重新统计）。

本包不分发商业资源；使用者必须从自己的 BFSE 安装取得 Voice3.pac。

### 4.2 脚本文本记录与 @v 控制码

文本记录基本结构确认：

```text
0B 00
uint32 little-endian 字符串长度
CP932 字符串
00
```

BFSE 并没有为主角剧情语音新增独立二进制 opcode，而是在现有文本开头直接加入控制标签：

```text
BFE ：@f1A0101「……ああ聞いているよ、月菜」
BFSE：@v500000@f1A0101「……ああ聞いているよ、月菜」
```

序章特殊独白：

```text
@h00@vTR0001
...
@h00@vTR0007
```

对原版 @v 处理入口的反汇编确认：BFE 只循环接受 '0'..'9'，再把读到的数字后面接上 .wav；BFSE 对应函数会无条件接收 @v 后面的前两个字符，再继续接收后四个字符，所以能处理 TR0001、KI0001 一类字母资源键。@h00 是 SE 新增控制码，原版不认识。

因此总体路线不是自己播放 WAV，而是让 BFE 继续走原生 @v 系统。

### 4.3 剧情运行时：0x0B 文本复制

```text
CALL site    ：VA 0x004AB5D2 / RVA 0x000AB5D2
原复制函数   ：VA 0x004ACC20 / RVA 0x000ACC20
```

运行时状态字段（已由原版反汇编确认）：

```text
state + 0x0C  = 脚本执行流长度
state + 0x114 = 当前读取游标
state + 0x128 = 脚本执行流基址
```

其中 state 由 self+8 取得，self 即被 Hook 的 __thiscall 第一个参数。

CALL 发生时 opcode 与 4 字节长度已经被解释器消费，游标正好指向字符串第一个字节，所以：

```text
recordOffset = cursorBeforeCopy - 6
```

临时文本槽布局：

```text
destination - 8 : opcode DWORD
destination - 4 : 字符串长度，含 NUL
destination     : 文本本体
```

临时槽容量约 0x1000 字节。查表前还做三项结构校验：记录不越过执行流末尾、记录开头确实是 0B 00、记录内的长度字段与本次 CALL 传入的 length 完全相同；任一项不符就保持原样。容量不足或校验不符时直接不注入，绝不越界。

### 4.4 剧情运行时：PAC 挂载

```text
CALL site      ：VA 0x004612BB / RVA 0x000612BB
原 PAC 打开函数：VA 0x004AE330 / RVA 0x000AE330
```

原版成功打开 Voice2.pac 后，用同一个 PAC manager self 再打开一次 Voice3.pac（self 相同是 BFSE 自身把 Voice1/Voice2/Voice3 挂在同一对象上的前提）。返回给原游戏的仍然是原 Voice2.pac 请求的结果；即使没有 Voice3.pac，也不把原资源初始化改成失败。另有一次性标志避免重复挂载。

### 4.5 剧情运行时：@v 参数解析与 TRxxxx 兼容

```text
@v 参数入口        ：VA 0x0049EA40 / RVA 0x0009EA40
数字原版继续点     ：VA 0x0049EA46 / RVA 0x0009EA46
TR 跳回播放流程点  ：VA 0x0049EAF9 / RVA 0x0009EAF9
```

被覆盖的 6 字节原机器码：

```text
8A 5C 08 02    mov bl, [eax+ecx+2]
33 D2          xor edx, edx
```

补丁形式为 E9 rel32 + 1 字节 90（NOP），覆盖两条原指令。

TR 分支的汇编级细节（必须继续使用原解析函数当前那一帧，所以用 naked 函数）：

- 只在 bl == 'T' 且 [eax+ecx+3] == 'R' 时接管，否则执行 xor edx, edx 后跳回 0x0049EA46，数字 VoiceTag 100% 走原版；
- edx = eax + ecx + 2，即 @v 后面的 6 字节资源键；
- 语音文件名临时缓冲区原本在 [原 ESP + 0xA4]，push ebx 之后同一地址是 [当前 ESP + 0xA8]；
- 复制 6 字节键，其后写入 0x7661772E（小端即 .wav）与结尾 NUL；
- 同步维护 this+0x60 的当前语音文件名，共复制 11 字节（TR0001.wav + NUL），供「重播上一句」等后续逻辑使用；
- add dword ptr [ebp+0xE8], 6 前移文本游标以吃掉整整 6 字节键（原版公共尾部还会再 +2 吃掉 @v 本身）；
- 跳过原版仅针对既有角色的语音可用性检查，但保留原版的「当前模式」与「语音忙碌状态」检查。

成功方案固定为：文本只注入 @vTR0001，只在 0x0049EA40 接管 TR。

### 4.6 旧汉化 BFET 与身份键

旧汉化会把 BFET 数据追加到真正执行流之后。BIN 头确认：

```text
stream_start = 16 + (u32@0x08 * 4)
stream_size  = u32@0x0C
```

序章汉化文件总长度会增长，但真正执行流长度保持原来的范围。

所以正式身份键只使用：

```text
FNV-1a32(真正执行流)
+
0x000B 记录相对执行流的偏移
```

FNV-1a32 参数：偏移基准 0x811C9DC5，质数 0x01000193，逐字节 XOR 后相乘，与离线生成器完全一致。

不哈希整个文件，也不比较最终正文（日文或中文），因此同一份脚本的原始日文版与旧汉化版得到同一个身份哈希。运行时查找用二分（最多约 log2(5891) ≈ 13 次比较）。

### 4.7 BFE 与 BFSE 脚本总体差异

```text
BFE BIN           ：301 个
BFSE BIN          ：280 个
忽略大小写共同脚本：279 个
BFE 独有          ：22 个（after.bin、Replay21 ~ Replay41）
BFSE 独有         ：ren01b.bin
```

BFSE 另有若干极小占位 BIN，没有可提取的正常文本记录。

不能用「BFSE 第 N 句 = BFE 第 N 句」直接迁移，因为 SE 有全年龄改写、演出调整和局部结构变动。离线映射综合了文本相似度、前后文、局部序列、剧情锚点和人工正/负样本；允许连续上下文中的改写，不允许只因孤立短句相似就强行配对。

### 4.8 Battle Voice 逆向结论（不进入运行时）

资源结构：BFSE Dat\BatVoice\tooru.dat 确认固定结构：

```text
48 slots × 32 bytes = 0x600 = 1536 bytes
35 个非空常规槽 / 13 个空槽
```

用户提供的 BFSE Se\Voice 主角 WAV 共 48 个。35 个非空槽引用的 WAV 35/35 都存在；另外 13 个不被 DAT 直接引用：

```text
tooru0101B.wav  tooru0102B.wav  tooru0102C.wav  tooru0103A.wav
tooru0104B.wav  tooru0111.wav   tooru0211.wav   tooru0311.wav
tooru0411.wav   tooru0511.wav   tooru0611.wav   tooru0711.wav
tooru0811.wav
```

尚未证明这 13 个在 BFSE 运行时是否被另一条路径使用；不要擅自给它们设计触发。两个 bachelor 相关资源经二进制比较在 BFE/BFSE 中完全一致，已排除为新增主角语音载体。

BFE Battle Voice loader 与调用点：

```text
loader            ：VA 0x0043ED30 / RVA 0x0003ED30
正确 CALL site    ：VA 0x0041BBB5 / RVA 0x0001BBB5
该处原字节        ：E8 76 31 02 00（目标即 0x0043ED30）
loader 内 SoundLoad CALL：VA 0x0043EEC4 -> VA 0x004A99C0
```

Battle state：

```text
base  = VA 0x00535550
stride = 0xDC
+0x18 = ref / 首次初始化计数
+0x1C .. +0xD8 = 48 个声音对象指针
```

已用实验确认/使用过的对象层地址：

```text
0x004B0ED7  原版分配器
0x004A9710  BattleSound 对象构造
0x004A99C0  SoundLoad
0x004A9720  one-shot play
0x004A9750  loop play
0x004A9790  replay
0x004C01E8  BattleSound vtable
```

BattleVoiceSelect 对比：

```text
BFE selector ：VA 0x004559A0
BFSE selector：VA 0x00458250
全局 CALL 统计：BFE 9 个调用点 / BFSE 10 个调用点（原有 9 个可对应）
```

BFSE 多出的入口在 VA 0x004475D1 附近，核心调用：

```asm
push -1
push 0
push esi
call 0x00458250
```

即 BattleVoiceSelect(actor, category=0, variant=-1)。BFE 同源位置约 VA 0x0043F321 / RVA 0x0003F321，没有这条调用。

category 0 对应 tooru.dat 前 4 个槽：

```text
slot 0 tooru0101A.wav
slot 1 tooru0102A.wav
slot 2 tooru0103B.wav
slot 3 tooru0104A.wav
```

## 5. 已成功方案

### 5.1 剧情语音主链（v0.1.0 冻结，v0.1.1-test1 沿用）

1. **Voice3 同 manager 挂载**：原版 Voice2.pac 成功后，用同一 self 追加打开 Voice3.pac。test1 实机确认挂载成功、普通数字主角剧情语音正常、Backlog 正常。
2. **数字 @v 完全走原版**：运行时只前插 @v500000 这类数字标签，播放、模式判断、忙碌判断、Backlog 全部交还原版。
3. **TRxxxx 最小兼容**：test2 实机确认 TR0001～TR0007 正常，Backlog 正常，普通数字主角语音无回归。
4. **运行时身份键**：FNV-1a32(真正执行流) + 0x000B 记录静态偏移，与正文语言无关，兼容旧汉化 BFET 追加。
5. **只改内存临时字符串**：磁盘 BIN 永远不写；注入失败（容量不足、结构校验不符）时宁可不播。
6. **正式发行清理**：v0.1.0 相对 test3 只删除日志、覆盖率统计与运行时 CSV，重新生成后 5855 条 VoiceMap 与 test3 **逐条完全相同**。
7. **长上下文唯一定位**：本轮把待定位候选窗口从前后 5 条扩到前后 20 条，19 条据此唯一确认并加入映射。
8. **静态验证**：verify_build.py 对最终 ASI 检查 PE32/i386、DLL 标志、非零入口、空标准导入表和两个导出名，当前全部通过。

### 5.2 Battle Voice 已成功部分（未进入任何发行版）

1. **资源/声音对象层闭合（test10）**：改为「ASI 内嵌 WAV -> 单次临时物化到 ASI 目录 -> 把真实路径交给原版 0x004A99C0 -> Load 完立即删除临时 WAV」，实机结果 35/35 SoundLoad 成功、35 个 BattleSound 对象有效、35/35 临时 WAV 写入与删除成功；主动 slot0 one-shot probe 能听到主角语音。
2. **自然播放审计（test11）**：删除所有主动 probe，只 Hook vtable +0x08（one-shot 0x004A9720）、+0x0C（loop 0x004A9750）、+0x18（replay 0x004A9790），仅当 this 属于主角 48 槽对象时记录。一次实机只观察到 mode=once / slot=14 / tooru0402A.wav / callerRVA=0x00055B61，用户听感是只有必杀技附近出现少量语音。
3. **普通攻击语音恢复（test12）**：在 BFE 同源位置补回 BFSE 唯一新增的 category-0 调用，不自己选句子，继续交给 BFE 同源 selector。用户实机确认普通攻击开始有语音；日志 battleCategory0CompatCalls=5，自然播放中出现 slot 0、slot 3、slot 2，并叠加原 BFE 既有的 slot 12 事件触发。

这三步证明战斗语音在技术上可以做到很接近 BFSE，但没有完成行为等价审计，因此不作为「完全复刻 BFSE」的结论。

## 6. 已失败与已证伪方案

### 6.1 test1：直接注入 @h00@vTR0001

结果：@h00 原版不认识、TR 也不符合数字参数，画面出现 00TR0001，没有 TR 音频。原因定位为原版 @v parser 不支持字母键。此后固定为「只注入 @vTR0001 + 在 0x0049EA40 接管 TR」。

### 6.2 Battle Voice 早期实验中的错误地址

```text
错误 CALL-site RVA 0x0001ABB5 -> test6 等早期实验实际没有 Hook 到目标
错误 loader RVA    0x0003DD30 -> 也曾导致安全校验拒绝
```

正确值见 4.8：CALL site RVA 0x0001BBB5、loader RVA 0x0003ED30。

### 6.3 test8：按路径虚拟文件方案

BFSE tooru.dat 已选中，但最初按路径虚拟文件的方案没有进入预期文件 Hook，方案未达成。

### 6.4 test9：直接建立 35 个对象壳

35/35 SoundLoad("Se\Voice\...") 失败。结论：**「对象指针非空」不能等价于「音频加载成功」**。这也是后续日志把「对象建立」和「SoundLoad 成功」拆开统计的原因。

### 6.5 test10 的边界：主动 probe 不是自然行为

probe 在进入游戏阶段也会响，因为那是测试代码主动调用。所以 test10 只能证明资源/对象/播放函数可用，**不能证明触发时机正确**。

### 6.6 不重写 / 不重编译 BIN

用户的旧汉化已经修改过 BFE BIN。再次反编译/重编译存在：跳转与指针重算风险、BFET 尾部结构被破坏风险、与旧汉化正文冲突、不同版本脚本结构错位、回滚与分发复杂度增加；同引擎历史工具也出现过 Baldr Force 脚本 pointer fix 问题。该路线已放弃，磁盘 BIN 永远不写。

### 6.7 已排除但未证伪的项

- Replay 中虽观察到约 289 次主角 VoiceTag 使用（**待确认**：重组前研究记录值，本轮未重新统计），但主要复用普通剧情资源，未完成与 BFE Replay 的人工确认，因此不纳入当前运行时映射；
- 前后各 20 条仍不能唯一定位的 9 条（见 9.2）继续排除；
- ren47c.bin 4 条一对多 VoiceTag 冲突继续整条排除，不做猜测；
- 13 个 tooru.dat 之外的 WAV 未证明真实调用者，不设计触发；
- 原版初始化日志中的 Movie.pac -> NOT_FOUND、Se.pac -> NOT_FOUND（Se_Adv.pac -> OK）是原版非致命资源探测，**不是**主角语音失败根因，也不影响当前资源初始化与剧情语音运行。

### 6.8 正式停止 Battle Voice 的原因

用户最终判断：战斗语音投入太多、实际收益太少，为完全复刻 BFSE 行为继续做事件级 A/B 审计不值得。因此 v0.1.0 回到纯剧情 test3 基线，战斗研究只保留文档，不保留运行时代码。

## 7. 运行架构

source\BaldrForceVoiceSE\src\BaldrForceVoiceSE.cpp 只有三条核心 Hook：

1. **Script CALL Hook**（0x000AB5D2）：识别安全 VoiceMap、调用原字符串复制函数、在临时文本前插 @v；
2. **PAC Open CALL Hook**（0x000612BB）：原请求先照常执行，Voice2.pac 成功后再追加 Voice3.pac；
3. **TR @v parser Hook**（0x0009EA40 机器码补丁）：只接管 TRxxxx，数字型 VoiceTag 立即回原版。

没有任何战斗 Hook、文件日志 API、CSV writer 或运行时审计数组。

初始化与自保机制：

- 入口有两个：导出 InitializeASI 与 DllMainCRTStartup（reason == 1，即 DLL_PROCESS_ATTACH）；初始化幂等，重复进入直接返回，不会把 CALL 补两次；
- 无标准导入表：VirtualProtect、FlushInstructionCache 由运行时从 PEB 模块链表手工解析导出表取得（fs:[0x30] -> PEB -> +0x0C LDR -> +0x0C InLoadOrder 链表 -> 条目 +0x18 DllBase；导出目录 IMAGE_EXPORT_DIRECTORY 的 +0x18/+0x1C/+0x20/+0x24；遇到 forwarder 字符串则继续扫描其它已加载模块，模块数硬上限 256）；链接使用 /nodefaultlib，不依赖 VC Runtime；
- 补丁前逐项校验目标机器码/旧 CALL 目标：CALL 补丁要求首字节为 0xE8 且当前目标等于已逆向确认的原函数；TR 补丁要求前 6 字节精确匹配。不符即安静拒绝写入，不盲写未知代码；
- 修改代码页前用 VirtualProtect 临时改为 PAGE_EXECUTE_READWRITE（0x40），写完恢复原保护属性，并调用 FlushInstructionCache(-1, ...) 刷新指令缓存；
- 不依赖 CRT：自带最小 memcpy（编译器可能把拷贝循环合成为 memcpy 调用），用自写 StringEquals/StringLength 代替 strcmp/strlen；编译期另加 -fno-builtin-strlen，防止 clang 22 把循环合成为 strlen 而在 /nodefaultlib 下出现 undefined symbol: _strlen；
- 与既有汉化 ASI 共存：Hook 只改「已经复制到临时缓冲的本次文本」，原复制函数仍被调用，源游标不被改动，读档/跳转/回看不会让「第几句」计数错位；
- 缺资源时降级：没有 Voice3.pac 时最坏只是新增主角语音不播放，不会让原版资源初始化失败。

## 8. 使用与配置

安装：

1. 需要能够加载 32 位 ASI 的 Loader，把 BaldrForceVoiceSE.asi 放到 Loader 会加载的位置；
2. 从自己的 BFSE 安装取得 Voice3.pac，放到 BFE 原版 Voice1.pac、Voice2.pac 所在的同一资源位置。本包不附带 Voice3.pac。

本模块**没有配置文件**：release 中不产生 BaldrForceVoiceSE.ini（对比 BGMSE/CN/Gamepad 各有 INI）。

运行时不生成任何文件：

```text
BaldrForceVoiceSE.log
BaldrForceVoiceSE_Coverage.csv
```

source\BaldrForceVoiceSE\data 下的 CSV/XLSX 是离线接档与复核资料，不是游戏运行时输出。

版本选择：只想使用已冻结的正式版本就继续用 v0.1.0；愿意帮助验证此前缺失的少量语音位置才用本测试版。

## 10. 测试要点与通过标准

本轮重点不是重跑完整游戏，而是确认新补回的 36 条是否在**正确剧情节点**播放。优先关注全年龄版与成人版改写幅度很大的场景：

```text
ayane03.bin  bachelor06.bin  bachelor22.bin  ren22.bin
ren45.bin    ren47c.bin      tsukina30.bin   tsukina35.bin
```

推荐顺序：

1. 优先走 前后20条定位通过.csv 中 19 条大幅改写场景；
2. 确认语音没有提前/延后到同场景另一句主角台词；
3. 打开 Backlog 重播，确认仍是同一句语音；
4. 抽查 v0.1.0 原有剧情语音，确认没有回归；
5. 若 36 条均通过，再把本测试版映射冻结为下一正式版。

通过标准：

- 每条映射对应的 BFE 台词在进入时播放对应 BFSE 语音；
- 语音内容本身正确且落在同一事件节点，不漏播到相邻台词；
- Backlog 回放的是同一条语音；
- v0.1.0 已确认的剧情语音无回归；
- 不出现漏出控制码文本（如 00TR0001）的情况。

如果发现某条语音内容没错、但播放到了同一场景里的错误一句，请记录脚本名与大致剧情位置；这正是本测试版要排除的剩余风险。
