# BaldrForceBGMSE v0.1-test1 完整接档说明

> 本文是截至 v0.1-test1 的累计接档文档。单独拿到本包即可理解目标、逆向结论、地址、数据结构、成功方案、被否定方案、当前测试状态、构建方法和下一步。

## 1. 项目目标

目标是把 `BALDR FORCE Standard Edition`（BFSE）的新版 BGM 移植进 2003 原版 `BALDR FORCE`（BFE），但继续保留 BFE 自己的：

- BGM ID；
- 剧情什么时候切歌；
- 淡入淡出；
- 音量控制；
- 暂停/恢复；
- 其它播放状态机。

用户观察到两版 BGM：

- 曲目数量完全相同；
- 编号位置相同；
- 实际用途/场景听起来一一对应；
- 主要差别是 PAC 内资源文件名完全不同。

逆向后确认这种“按编号一一对应”的理解与 EXE 代码吻合。

## 3. BGMInfo.DAT 结构

两版完全同型：

```text
30 × 0x44 = 2040
+ 9 字节共同表尾
= 2049
```

每条：

```cpp
struct BGMInfoEntry
{
    char  resourceName[0x40];
    int32 loopStartCs;
};
```

### `resourceName[0x40]`

CP932、NUL 结尾，是 PAC 内 WAV 资源名。

两版编号一致但资源名不同，例如：

```text
#05 BFE  05：リアル・ワールド.wav
#05 BFSE 05：the real world.wav

#13 BFE  13：DANGER ZONE.wav
#13 BFSE 13：Red Zone.wav

#26 BFE  26：運命の皮肉.wav
#26 BFSE 26：irony of fate.wav

#27 BFE  27：リバイアサン.wav
#27 BFSE 27：Leviathan.wav
```

### `loopStartCs`

已确认是循环起点，单位 1/100 秒：

```text
-1   = 非循环
0    = 从曲首循环
1548 = 15.48 秒
3999 = 39.99 秒
5458 = 54.58 秒
```

BFSE：

```text
#01~#28 >= 0
#29~#30 = -1
```

即 28 首循环、2 首非循环。

## 4. 循环点机器码证据

### BFE BGM ID -> BGMInfo

BFE 播放入口会把 BGM 编号乘以 0x44：

```text
BGMInfo[index] = 0x00721010 + index * 0x44
```

相关播放路径：

```text
VA 0x00463850
VA 0x00463980
```

### 读取 +0x40

例如第一条播放路径：

```text
0x00463905  mov eax,[edi+0x721050]
0x0046390F  mov edi,[edi+0x721050]
```

`0x721050 = 0x721010 + 0x40`。

### 小于 0

```text
0x00463918  test edi,edi
0x00463918/1A 分支
```

小于 0 时调用：

```text
0x004AD980
```

函数内部：

```text
object +0x30 = 0
```

即不使用循环回卷。

### 大于等于 0

调用：

```text
0x004ADA10
```

函数内部：

```text
object +0x30 = 1
object +0x34 = loopStart
```

### 文件读到尾部后的回卷

流读取代码：

```text
0x004AD3F7  cmp [ecx+0x30],1
0x004AD3FC  mov edx,[ecx+0x34]
```

随后执行：

```text
loopStart * [object+0x28] / 100
```

计算字节位置。

机器码常数：

```text
0x51EB851F
```

配合高位乘法与右移实现除以 100。

所以 +0x40 的时间单位已经闭合为 1/100 秒，不应再写成“未知参数”。


## 6. BGM loader 地址

BFE 真正加载一首 BGM WAV 的原函数：

```text
VA 0x004AD7F0
RVA 0x000AD7F0
```

全 EXE 直接 CALL 该函数只有两处：

```text
VA 0x00463892 / RVA 0x00063892
VA 0x004639B6 / RVA 0x000639B6
```

这两个 CALL 都来自 BGM 播放控制路径。

原 loader 的关键行为：

- 第一个栈参数是资源上下文；
- 第二个栈参数是 BGMInfo 记录起点；
- loader 把第二参数直接当 NUL 结尾资源名字符串，交给通用资源打开函数；
- loader 本身不读取 `record+0x40`。

这个事实使“保留 BFE 内存名字，只在 loader 参数上临时换 BFSE 名字”成为可行方案。

## 7. 汉化版 BGM 名称兼容策略

用户指出汉化版程序里 BGM 名字已经汉化，因此不能只考虑“能否找到 BFSE WAV”。

最初曾考虑：

```text
把 BFE 30×0x44 整条覆盖成 BFSE 记录
```

该方案虽然能同时带来 BFSE 文件名和循环点，但有一个潜在副作用：

```text
如果某个 UI/鉴赏界面从 BGMInfo 前0x40 取名字，
就会把 BFE/汉化名换成 BFSE 英文资源名。
```

因此 v0.1-test1 **没有采用整条覆盖**。

当前方案：

```text
BFE BGMInfo 内存：
  +0x00..0x3F 完全保持原值
  +0x40       替换为 BFSE loopStartCs

真正调用 0x004AD7F0：
  只把资源名参数临时改成 BFSE resourceName
```

这样既满足 BFSE PAC 资源名，又尽量不碰 BFE/汉化版名称数据。

## 8. 两种 BGM.pac 来源模式

用户当前使用 Ultimate ASI Loader，并能把 BFSE 原版 `BGM.pac` 放在 `update` 中虚拟覆盖原文件。

所以插件固定支持两种模式。

### 8.1 Game 模式

```ini
[BGMSE]
Source=Game
```

行为：

- 不 Hook CreateFileA；
- 不修改任何 BGM.pac 路径；
- 游戏继续打开原路径 `BGM.pac`；
- Ultimate ASI Loader 如果虚拟覆盖，就自然得到 update 内 BFSE BGM.pac。

这是默认模式。

### 8.2 Local 模式

```ini
[BGMSE]
Source=Local
```

插件修改 BFE 主 EXE 的 CreateFileA IAT：

```text
IAT RVA 0x000BE05C
```

只要 basename 等于：

```text
BGM.pac
```

就改读：

```text
ASI 同目录\BFSE_BGM.pac
```

其它文件全部原样传给原 IAT 函数。

为了和 Ultimate ASI Loader/其它文件系统 Hook 共存，插件保存的是**安装时 IAT 槽里的当前函数指针**，而不是强制绕过现有链直接调用一个固定 kernel32 地址。

如果本地 BFSE_BGM.pac 打不开，test1 会：

1. 写日志；
2. 回退原 BGM.pac；
3. 不让游戏因为路径错误直接启动失败。

## 9. BGMInfo Hook 实现

Hook：

```text
CALL VA 0x0046144C
```

原调用：

```cpp
TableRead(fileObject, destination, 0x44)
```

Hook 先调原函数，然后判断：

```text
size == 0x44
且 destination 位于 0x00721010 ~ 0x00721808
且 destination 正好对齐 0x44
```

再计算：

```text
index = (destination - 0x00721010) / 0x44
```

最后只写：

```text
destination + 0x40 = BFSE[index].loopStartCs
```

## 10. BGM loader Hook 实现

两处 CALL：

```text
0x00463892
0x004639B6
```

都改到同一个 `HookBgmLoad`。

Hook 收到 BFE 记录地址后：

```text
index = (recordPointer - BFE_BGM_TABLE) / 0x44
```

然后把第二参数换成：

```text
kBfseBgmInfo[index] 的起始地址
```

因为这 0x44 静态记录最前面就是 BFSE 文件名，原 loader 只把它当字符串。

## 11. 为什么不用改 Table.pac

不需要。

插件直接在 BFE 读完 BGMInfo 每条记录后修正循环点，文件系统里的 `Table.pac` 原封不动。

好处：

- 不污染游戏安装；
- 不需要重打包 NEXAS PAC；
- 不影响汉化版 Table.pac 的其它内容；
- 卸载 ASI 即恢复原行为。

## 12. 为什么不需要改剧情 BIN

BFE 剧情/系统逻辑只需要继续请求原 BGM ID。

BFE 和 BFSE 的播放代码都按：

```text
BGMInfo[index]
```

取对应曲目。

因此插件只在资源绑定层把：

```text
BFE index N
```

解释成：

```text
BFSE index N 的 WAV 文件名 + BFSE index N 的循环点
```

什么时候播放 N 号曲目完全不需要动。

## 13. BGM.pac 为什么不需要放进源码包

用户说明 BFSE `BGM.pac` 很大，不适合上传。

当前方案也不需要对它做静态分析：

- BGMInfo 已经给出 30 个 BFSE 资源文件名；
- 资源包由用户自己的 BFSE 安装提供；
- Game 模式由 UAL update 覆盖；
- Local 模式直接读取原封不动的 BFSE_BGM.pac。

因此插件包不包含商业 BGM 资源。

## 17. 已否定/修正的旧判断

### “+0x40 可能只是普通播放参数”

已修正。

它明确控制是否循环，并作为流到尾部后的重新读取起点，单位 1/100 秒。

### “只替换 BFSE 文件名就够”

已否定。

绝大多数 BFSE 循环点与 BFE 不同，只换 WAV 会导致循环位置错误。

### “整条 0x44 直接覆盖最简单”

技术上可行，但为了避免潜在汉化 BGM 名称显示回归，v0.1-test1 改为：

```text
表内只换 loopStart
loader 参数临时换 BFSE filename
```
