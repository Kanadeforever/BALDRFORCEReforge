## 2. 项目目标

把 BFSE 的新版 BGM 移植进 BFE，但**继续使用 BFE 自己的播放状态机**：

- BGM ID；
- 剧情什么时候切歌；
- 淡入淡出；
- 音量控制；
- 暂停 / 恢复；
- 其余播放状态。

观察与逆向互相印证：两版曲目数量完全相同（各 30 首）、编号位置相同、实际用途/场景一一对应，主要差别是 PAC 内资源文件名完全不同。逆向结果确认 BFE 与 BFSE 都以：

    BGMInfo[index]

按同一个 0~29 编号索引曲目，所以插件只在“资源绑定层”把 BFE 的编号 N 解释成 BFSE 编号 N 的 WAV 文件名与循环点，切歌时机完全交给原版代码。

## 4. BGMInfo.DAT 结构

两版同型：

    30 × 0x44 = 2040 bytes
    + 9 bytes 表尾
    = 2049 bytes

表尾两版完全相同：

    61 76 00 61 76 00 61 76 00
    即 "av\0av\0av\0"

BFE 的 BGMInfo 读取循环从 VA `0x00721010` 开始，每条读 `0x44`，终点比较地址 `0x00721808`，正好 30 条。这 9 字节表尾不属于 30 条运行时记录，插件不改它。

每条 0x44：

    struct BGMInfoEntry
    {
        char  resourceName[0x40]; // +0x00..+0x3F，CP932，NUL 结尾，PAC 内 WAV 资源名
        int32 loopStartCs;        // +0x40..+0x43，有符号；1/100 秒；-1 = 非循环
    };

内存布局：

    表起点        VA 0x00721010  RVA 0x00321010
    表字节数      30 × 0x44 = 2040
    表终点        VA 0x00721808
    BFSE 表起点   VA 0x0071CEB0（两版初始化算法同型）

两版编号一致、资源名不同。原值与换算秒数以 `source\BaldrForceBGMSE\data\BGM信息对照.csv` 为准（30 行，两版文件名与循环点并排）。抽样：

    编号  BFE 资源名                        BFSE 资源名                          BFE 循环点  BFSE 循环点
    #05   05：リアル・ワールド.wav           05：the real world.wav                  1066        1600
    #13   13：DANGER ZONE.wav                13：Red Zone.wav                        1324        1262
    #26   26：運命の皮肉.wav                 26：irony of fate.wav                   4914        4909
    #27   27：リバイアサン.wav               27：Leviathan.wav                       3454        4140

BFSE 30 首中 28 首循环、2 首非循环：

    #01~#28 loopStartCs >= 0
    #29、#30  loopStartCs = -1

## 5. 循环点语义的机器码证据

### 5.1 编号换算与 +0x40 读取

BFE 播放入口把 BGM 编号乘以 0x44 取得记录地址：

    BGMInfo[index] = 0x00721010 + index * 0x44

相关播放路径：

    VA 0x00463850
    VA 0x00463980

第一条路径读取 `+0x40` 的指令：

    0x00463905  mov eax,[edi+0x721050]
    0x0046390F  mov edi,[edi+0x721050]

`0x721050 = 0x721010 + 0x40`，即循环点字段。

### 5.2 分支

    0x00463918  test edi,edi
    0x00463918/0x0046391A  条件分支

- 值小于 0 → 调用 VA `0x004AD980`，函数内设置 `object +0x30 = 0`，不启用循环回卷，走非循环播放入口；
- 值大于等于 0 → 调用 VA `0x004ADA10`，函数内设置 `object +0x30 = 1`、`object +0x34 = BGMInfo +0x40 的值`。

### 5.3 文件到尾后的回卷

    0x004AD3F7  cmp [ecx+0x30],1
    0x004AD3FC  mov edx,[ecx+0x34]

随后按：

    loopValue * bytesPerSecond / 100

计算重新读取 WAV 数据的字节位置。除法由机器码常数 `0x51EB851F` 配合高位乘法与右移实现整数除以 100。

因为 `bytesPerSecond` 是每秒字节数，而循环点乘以每秒字节数再除以 100，所以 `loopValue` 的单位只能是 **1/100 秒**：

    1548 -> 15.48 秒
    1600 -> 16.00 秒
    3999 -> 39.99 秒
    5458 -> 54.58 秒
    -1   -> 不循环
    0    -> 从曲首循环

该语义已经闭合，不应再写成“未知参数”。

### 5.4 为什么循环点必须一起移植

两版循环点大量不同：

    编号   BFE      BFSE
    #02      0       1548
    #06   1600       3999
    #15      0       5458
    #20   2494        922
    #26   4914       4909
    #27   3454       4140
    #29     -1         -1
    #30     -1         -1

只把 BFSE 的 WAV 放进 PAC、仍沿用 BFE 循环点，绝大部分曲目会在错误时间回卷，甚至把 BFSE 的前奏/衔接结构切错。因此“文件名 + 循环点”被当作同一首 BFSE BGM 的配套元数据，必须一起移植。

## 6. 关键地址汇总

### 6.1 BGMInfo 初始化

    BGMInfo 初始化函数区域   VA 0x004613F0
    表读取 CALL              VA 0x0046144C  RVA 0x0006144C
    原目标（表读取函数）      VA 0x004A9EC0  RVA 0x000A9EC0
    原字节                    E8 6F 8A 04 00
    每条读取长度              0x44

### 6.2 BGM loader

    loader 函数               VA 0x004AD7F0  RVA 0x000AD7F0
    调用点 1                  VA 0x00463892  RVA 0x00063892
    调用点 2                  VA 0x004639B6  RVA 0x000639B6

全 EXE 直接 CALL `0x004AD7F0` 的位置**只有这两处**，且都来自 BGM 播放控制路径。

loader 的关键行为：

- 第一个栈参数是资源上下文；
- 第二个栈参数是 BGMInfo 记录起点；
- loader 把第二参数直接当 NUL 结尾资源名字符串，交给通用资源打开函数；
- **loader 本身不读取 `record+0x40`**。

循环控制由播放函数稍后从 BFE 表的 `+0x40` 独立读取。

### 6.3 Local 模式

    KERNEL32!CreateFileA 在 BFE 主 EXE 的 IAT 槽   RVA 0x000BE05C

### 6.4 循环分支与声音对象

    非循环入口   VA 0x004AD980   -> object +0x30 = 0
    循环入口     VA 0x004ADA10   -> object +0x30 = 1，object +0x34 = loopStart
    尾部判断     VA 0x004AD3F7   cmp [ecx+0x30],1
    取循环起点   VA 0x004AD3FC   mov edx,[ecx+0x34]
    除以 100     VA 0x004AD3F7 附近，常数 0x51EB851F

## 7. 已成功方案

### 7.1 运行期只改 +0x40，不改前 0x40 字节

内存里的 BFE BGMInfo：

    +0x00..+0x3F  完全保持 BFE/汉化版原值
    +0x40         替换为 BFSE 同编号 loopStartCs

### 7.2 只在 loader 参数上临时换 BFSE 文件名

真正进入 `0x004AD7F0` 时，才把第二参数（资源名指针）换成 BFSE 记录起点。因为 `kBfseBgmInfo[index]` 的前 0x40 字节就是以 NUL 结尾的 BFSE CP932 文件名，而 loader 只把它当字符串，所以直接传整条记录起点是安全的。

这样“资源文件名”和“界面可能使用的名称”被解耦，对汉化版影响最小。

### 7.3 Hook 之前先校验三个 CALL

安装前先把三个调用点全部验签，全部正确才开始写机器码：

    ValidateCall(0x0006144C -> 0x000A9EC0)
    ValidateCall(0x00063892 -> 0x000AD7F0)
    ValidateCall(0x000639B6 -> 0x000AD7F0)

验签方式是确认首字节为 `E8`，且后 4 字节相对位移解算出的目标等于期望 RVA。任何一处不匹配就整体放弃安装并写日志，避免拿错 EXE 时出现“前两个已改、第三个失败”的半补丁状态。

### 7.4 不修改 Table.pac

插件直接在 BFE 读完每条 BGMInfo 记录后修正循环点，文件系统里的 `Table.pac` 原封不动。好处：不污染游戏安装、不需要重打包 NEXAS PAC、不影响汉化版 Table.pac 的其它内容、卸载 ASI 即恢复原行为。

### 7.5 不修改剧情 BIN

BFE 剧情/系统逻辑继续请求原 BGM ID。BFE 与 BFSE 都按 `BGMInfo[index]` 取曲目，所以“什么时候播放 N 号曲目”完全不需要动。

### 7.6 Local 模式保存 IAT 槽现值而不是强写 kernel32 地址

为了和 Ultimate ASI Loader / 其它文件系统 Hook 共存，插件先保存安装时 IAT 槽里的当前函数指针作为调用链下游，再把自己的 Hook 写进槽位。这样不会绕过已有的虚拟文件系统。

### 7.7 无 CRT 构建

源码自己声明最小 Win32 类型，不包含 `windows.h`，从 PEB 找到已加载的 `kernel32.dll`，再解析导出函数（KERNEL32 转发到 KERNELBASE 时解析 `MODULE.Function` 转发字符串）。最终：

    Standard Import Directory = empty

需要的 API：VirtualProtect、FlushInstructionCache、GetModuleFileNameA、GetPrivateProfileStringA、CreateFileA、WriteFile、CloseHandle。

另外源码显式提供最小 `memcpy`/`memset`，避免 clang `/O2` 把复制/填充分配合成 CRT 调用后在 `/nodefaultlib` 下链接失败。

### 7.8 BGM.pac 不放进源码包

BFSE `BGM.pac` 体积大，也不需要对它做静态分析：

- BGMInfo 已给出 30 个 BFSE 资源文件名；
- 资源包由用户自己的 BFSE 安装提供；
- Game 模式由 Ultimate ASI Loader 的 update 覆盖；
- Local 模式直接读取原封不动的 `BFSE_BGM.pac`。

因此插件包不包含商业 BGM 资源。

## 8. 已失败与已证伪方案

### 8.1 “+0x40 可能只是普通播放参数” —— 已证伪

它明确控制是否循环，并作为流读到文件尾部后的重新读取起点，单位 1/100 秒（见第 5 节证据链）。

### 8.2 “只替换 BFSE 文件名就够” —— 已证伪

绝大多数 BFSE 循环点与 BFE 不同，只换 WAV 会导致循环位置错误。

### 8.3 “整条 0x44 直接覆盖成 BFSE 记录” —— 技术可行但被否决

能同时带来 BFSE 文件名和循环点，但有副作用风险：如果某个 UI/鉴赏界面从 BGMInfo 前 0x40 取名字，就会把 BFE/汉化名换成 BFSE 英文资源名。v0.1-test1 因此改为“表内只换 loopStart，loader 参数临时换文件名”。

### 8.4 “把 CreateFileA 强制改成直接调 kernel32 地址” —— 已否决

会绕过 Ultimate ASI Loader 等已有虚拟文件系统链。改为保存 IAT 槽现值并链式调用（见 7.6）。

### 8.5 本地 `BFSE_BGM.pac` 打不开时直接失败 —— 已否决

测试版改为：写日志 → 回退原 `BGM.pac` → 不让游戏因为路径错误启动失败。

### 8.6 旧文档引用过的构建脚本 —— 文件已不存在

旧文档中出现过的 `build_clang.bat`、`build_msvc.bat`、`build_clang_linux.sh` 在当前仓库中都不存在：

- `build_clang_linux.sh` 曾由作者主动删除（git 历史可查，且它属于 CN 模块而非本模块）；
- `build_clang.bat`、`build_msvc.bat` 从未进入过本仓库的 git 历史，无法通过 git 找回，其原始内容**待确认**；
- 当前唯一的构建入口是 `build_all.bat` 与各模块的 `build.bat`。

不要再按旧文档去找这三个脚本。

## 9. 运行架构

### 9.1 组成部分

1. 无 CRT 基础函数（字符串/内存/十进制格式化）；
2. PEB 模块枚举（`fs:[0x30]` → PEB → `+0x0C` PEB_LDR_DATA → `+0x14` InMemoryOrderModuleList → 条目 `+0x08` 回退 → `+0x18` DllBase / `+0x2C` BaseDllName UNICODE_STRING）；
3. PE Export 解析（含 `MODULE.Function` 转发解析，ordinal 转发即返回失败）；
4. Win32 API 动态解析；
5. 中文测试日志；
6. CALL / IAT 安全补丁（`VirtualProtect` → 改写 → 还原保护 → `FlushInstructionCache`）；
7. BGMInfo 循环点替换；
8. BGM loader 文件名替换；
9. Game / Local 两种 `BGM.pac` 来源。

源码：`source\BaldrForceBGMSE\src\BaldrForceBGMSE.cpp`（952 行，含详细中文行内注释）。

### 9.2 BGMInfo 循环点 Hook

Hook 目标：`CALL VA 0x0046144C`。原调用等价于 `TableRead(fileObject, destination, 0x44)`。

Hook 逻辑：

1. 先调用原函数，让 Table.pac 按原逻辑把记录读进内存；
2. 仅当 `size == 0x44` 且 `destination` 落在 `0x00721010 ~ 0x00721808` 且正好按 0x44 对齐时才处理；
3. `index = (destination - 0x00721010) / 0x44`；
4. 只写 `destination + 0x40 = BFSE[index].loopStartCs`；
5. 每个编号第一次被替换时写一条日志（30 位 bit mask 去重）。

不落在表内、长度不符、未对齐的一律原样返回，不做猜测。

### 9.3 BGM 资源名 Hook

两处 CALL：

    0x00463892
    0x004639B6

都改到同一个 `HookBgmLoad`。逻辑：

1. 由记录地址算 `index = (recordPointer - BFE_BGM_TABLE) / 0x44`；
2. 命中表内则把第二参数换成 `kBfseBgmInfo[index]` 的起始地址（前 0x40 字节就是 BFSE 文件名）；
3. 每个编号首次请求时写一条日志；
4. **参数不在表内时原样交回 BFE**，宁可播放原资源也不猜编号。

### 9.4 Local 模式 Hook

INI 为 `Source=Local` 时，把主 EXE IAT 槽 `RVA 0x000BE05C` 换成 `HookCreateFileA`：

- 只拦截 basename 等于 `BGM.pac`（大小写不敏感，`\\` 与 `/` 都算分隔符）的请求；
- 命中则改读 ASI 同目录 `BFSE_BGM.pac`；
- 其它文件全部原样传给链上下游函数；
- 本地文件打开失败时写一条警告日志并回退原路径。

Game 模式完全不碰这个 IAT 槽。

### 9.5 导出与入口

    InitializeASI        （.def 中导出，同时可见 _InitializeASI@0）
    DllMainCRTStartup    （/entry:DllMainCRTStartup@12，DLL_PROCESS_ATTACH 时初始化，DETACH 时关闭日志）

## 10. 使用与配置

### 10.1 需要的文件

本包不附带 BFSE 的 `BGM.pac`。需要从自己的 BFSE 安装中取得原始 `BGM.pac`，**不要解包，不要重新压包**。

### 10.2 安装

把以下两个文件放到 Ultimate ASI Loader 会加载 ASI 的目录：

    BaldrForceBGMSE.asi
    BaldrForceBGMSE.ini

测试版运行后会在 ASI 同目录生成 `BaldrForceBGMSE.log`，内容为中文 UTF-8 文本。

### 10.3 Game 模式（默认，推荐先测）

    [BGMSE]
    Source=Game

把 BFSE 原始 `BGM.pac` 按当前 Ultimate ASI Loader 的规则放进 `update`，让它虚拟覆盖游戏原来的 `BGM.pac`。插件此时**完全不接管 `BGM.pac` 路径**，只负责：

- BFE BGM 编号 → BFSE 同编号资源名；
- BFE 循环点 → BFSE 同编号循环点。

最终文件来源仍由 Ultimate ASI Loader 的虚拟文件系统决定。

### 10.4 Local 模式

    [BGMSE]
    Source=Local

把 BFSE 原始 `BGM.pac` 重命名为 `BFSE_BGM.pac`，与 ASI、INI 放在同一目录：

    BaldrForceBGMSE.asi
    BaldrForceBGMSE.ini
    BFSE_BGM.pac

插件只拦截 basename 为 `BGM.pac` 的 CreateFileA 请求，其它游戏文件原样传递。

### 10.5 INI 说明

INI 随包内容（`source\BaldrForceBGMSE\templete\BaldrForceBGMSE.ini`，287 字节，构建时复制到 release）：

    [BGMSE]
    ; Game：直接读取游戏看到的 BGM.pac。
    ;       如果使用 Ultimate ASI Loader 的 update 虚拟覆盖，把 BFSE 的 BGM.pac 作为 update\BGM.pac 即可。
    ; Local：忽略游戏的 BGM.pac 路径；改读 BaldrForceBGMSE.asi 同目录的 BFSE_BGM.pac。
    Source=Game

读取方式为 `GetPrivateProfileStringA("BGMSE", "Source", "Game", ...)`。

- 只有取值等于 `Local`（或 `1`，大小写不敏感）才进入 Local 模式；
- 其它任何取值、INI 缺失、INI 读不到，都按 Game 模式运行。

### 10.6 日志

日志写入 ASI 同目录 `BaldrForceBGMSE.log`，`CREATE_ALWAYS`（每次启动覆盖），行尾 `\r\n`。三类日志：

启动：

## 11. 测试要点与通过标准

推荐顺序：先 Game 模式（最贴近当前实际使用方式），再 Local 模式。

### 11.1 启动阶段

- 游戏能正常启动进入；
- 日志出现 `[启动]`、`[成功] 已安装 ... Hook`、`[模式]`、`[完成] 初始化成功`；
- 游戏读取 `BGMInfo.dat` 后，30 条 `[BGMInfo] 已替换 #n` 依次出现且编号 1~30 无缺号。

### 11.2 播放阶段

- 某编号第一次被请求时出现对应 `[BGM资源] 首次请求 BFSE 曲目 #N`；
- 实际听到的是 BFSE 版本 BGM，不是 BFE 原版。

### 11.3 循环测试（本轮最重要的验证项）

不能只听“有没有换歌”。建议专门听循环点明显的曲目：

    #06  loop=3999 -> 39.99 秒
    #15  loop=5458 -> 54.58 秒
    #26  loop=4909 -> 49.09 秒
    #27  loop=4140 -> 41.40 秒

需要确认：

- 第一次播放从曲首开始；
- 播到尾部后不是回到 0，而是回到 BFSE 指定循环点；
- 没有明显爆音、断裂、错拍；
- 没有回到 BFE 原循环位置。

`#29`、`#30` 循环点为 `-1`，应保持非循环行为。

### 11.4 汉化版曲名

本版特意不覆盖 BFE 内存 BGMInfo 的前 0x40 字节，所以如果汉化版 BGM 显示名来自 BFE 自己的数据，这些文本应继续保持汉化状态。请检查游戏内能看到 BGM 名称的界面；显示完全没变化即证明这层兼容设计成立。

### 11.5 两种模式

Game 模式必须跟随 update 虚拟覆盖；Local 模式必须正确重定向到 `BFSE_BGM.pac`。两者切换只需要改 INI。

### 11.6 共存

与现有 VoiceSE、汉化等 ASI 同时加载时不应互相破坏。

### 11.7 失败时需要提供什么

只需要：

    BaldrForceBGMSE.log

如果只是某首歌不播放，再补充大概是第几首 / 哪个场景即可。
