# 脚本复制语义与崩溃调查说明

> 截至 `v1.0.4-crashfix1` 的累计结论。

## 1. opcode 0x0B 已确认结构

34,184 条 BFET 源字符串都能对应到脚本中的 opcode `0x0B` 字符串对象。当前 Hook 位于 clean 2003 `0x004ACC20`，核心对象布局：

```text
dest-8  = value type，正常为 0x0000000B
dest-4  = 运行时字符串 byte_count（包含 NUL）
dest    = 字符缓冲区
state+0x114 = 脚本源读取游标
state+0x0C  = 当前脚本上限
state+0x128 = 当前脚本 body
```

## 2. v1.0.2 的结论为什么只对了一半

旧 46MB 汉化反编译证明，翻译不能改变**脚本源流的消费位置**：原脚本里 count 是多少，`state+0x114` 就必须加多少，否则下一条 opcode 会错位。v1.0.2 因此停止用中文长度推进脚本，这部分是正确且继续保留的。

但 v1.0.3 的第二次实机日志证明，我们错误地把这个结论扩大成了“运行时 value object 的 byte_count 也必须永远保留原 count”。这会让 Backlog/历史记录等二次消费者拿到错误长度。

## 3. #64 是决定性证据

`jyosyo05.bin #64`：

```text
JA: @f1A0121「………な」      20 bytes
ZH: @f1A0121「………什么……」  26 bytes
原脚本 count = 21
```

v1.0.3 主显示已经把 26 个 GBK 字节写进对象，但 `dest-4` 仍为 21。用户看到结尾缺符号/方块，随后打开 Backlog 崩溃；完整日志再次命中 #64，并显示该长度差会在 GBK 双字节中间截断。

因此当前正确模型是：

```text
源脚本 count：21
    -> 只用于 state+0x114 += 21

中文运行时 byte_count：27
    -> 写入 dest-4
    -> 供显示、Backlog、历史记录、再次复制使用
```

两者不能混用。

## 4. 当前 Hook 规则

命中 BFET 或 after.bin direct-entry 时：

1. 先验证 `count <= limit-cur`，防止 Hook 自己越过脚本 body；
2. 脚本游标按原 `count` 前进；
3. 把中文 GBK 写到 `dest` 并补 NUL；
4. 把 `dest-4` 更新为 `中文长度+1`；
5. 注册 GBK provenance/range；
6. 诊断事件同时保存原 count 与更新后的 value_count。

未命中翻译时，按原 count 原样复制，不改内容。

## 5. 全量长度审计仍有意义

固定统计：34,184 条中 3,909 等长、29,633 中文更短、642 中文更长。若某个二次消费者错误绕过 value object、直接拿源 count 截中文，642 条扩张文本中有 627 条会切进 GBK 双字节。因此 `audit_bfet_backlog_risks.py` 继续保留，作为以后发现其它错误消费者时的风险地图。

## 6. 八木泽名片不是同一个根因

第一次 v1.0.3 日志在 `jyosyo05.bin #49` 71->71 后崩溃，真实 EIP 为主程序 `0x0048A974`，读取地址 `0xFFFFFFFF`，且 `glyph_failures=1`。它没有表现出脚本源错位；该故障已转到“GBK 字形失败后错误回退 CP932”修复线。不要再把两个崩溃合成一个 byte_count 问题。
