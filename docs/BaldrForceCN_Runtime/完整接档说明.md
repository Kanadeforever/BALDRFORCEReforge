## 2. 发行文件与可选配置

`release\` 现在恰好四个文件：

```text

```

INI 与日志都按 ASI 自身目录定位。Update/Chapter 仍由游戏主目录原生 PAC 体系使用。

## 3. 资源架构

旧 46MB 汉化 VFS 共 313 文件、45,599,439 bytes。用户把除两个 PAC 外的 311 loose 文件与 clean 原版逐字节比较：只有 9 个不同，302 个完全相同。因此最终覆盖是 `2 PAC + 9 loose = 11 COVERED`，其余 302 PASS，0 REVIEW。

9 个 ASI 内嵌差异 loose：

```text

```

ASI 用 `.incbin` 原字节嵌入；命中白名单路径时生成隐藏、delete-on-close 的真实 Windows backing file，返回真实 HANDLE。其它 loose 资源全部走原版。

`Update.pac` 固定：23,984,401 bytes，SHA256 `7f5f66e03d23869aeb2c8de771f4d34907478a85cfa8982e9da9c64612c4114e`。`Chapter.pac` 固定：8,129,004 bytes，SHA256 `565e48a1a272feb9c99223f0a5dac8e3a450dea4a5ce05e8e81e8e400b9e960d`。

`after.bin` 是旧汉化新增且被汉化 `Title.bin` 真实引用的脚本，原版不存在。它保留在 Update.pac，因无 BFET 而由 direct-entry 提供直接 GBK；首次执行会写 `[命中] after.bin...`。

## 4. 文本/脚本架构

Update.pac 含 301 个 `.bin`，其中 300 个有有效 BFET，建立 34,184 条 JA(CP932)->ZH(GBK) 映射。主翻译 Hook 位于 clean `0x004ACC20`，对应 opcode 0x0B 字符串复制。

当前正确“双长度”语义：

```text
state+0x114  脚本源游标：按原日文 count 前进
dest-4       运行时对象 byte_count：写中文实际字节数 + NUL
dest         写中文原始 GBK + NUL
```

这一结论来自第二份 v1.0.3 实机日志。#64 日文 20 bytes、中文 26 bytes、源 count=21；v1.0.3 value object 仍为 21 时出现末尾方块并在打开 Backlog 后崩溃。v1.0.4 将对象 count 更新为 27，但源游标仍加 21。

全量长度统计：3909 等长、29633 中文更短、642 中文更长。若某个其它消费者错误复用源 count 截译文，642 条中 627 条会截在 GBK 双字节中间。风险 CSV/工具继续保留。

## 5. 普通 GBK renderer

全局 renderer 关键 Hook：`0x00489726 / 0x00489852 / 0x00489897`。旧汉化规则已确认：lead byte `0x80..0xFE` 均按双字节消费。此前已实机证明主体中文显示正常。

v1.0.3 第一次崩溃现场：

```text
EIP=0x0048A974
AccessViolation READ 0xFFFFFFFF
最后脚本 jyosyo05.bin #49 71->71
glyph_failures=1
```

这说明某个 GBK glyph 失败后错误回落到原版 CP932 renderer。v1.0.4 的安全策略：

1. 默认仍优先 `GetGlyphOutlineA` + GB2312，最大限度保持既有视觉；
2. ANSI 失败时将 GBK bytes 用 CP936 转 Unicode；
3. 用 `GetGlyphOutlineW` 重取；
4. 若仍失败，返回合法全 0 字形/掩码；
5. 已确认 GBK 的字符绝不再因为缺字返回 NULL 去走 CP932 fallback。

用户配置 FontFace 时，GBK glyph 直接优先用 Unicode 字体 DC，避免字体名受系统 ANSI 代码页影响。

## 10. 已失败/已证伪方案与坑

- 把旧 46MB 的 `0x53400xx` 签名直接用于 clean `0x53500xx`：test9 Hook 0/0；
- 只在 glyph lookup 入口捕获字符、不修上游 Shift-JIS 分组：test10 得到 `CF | E0C2 | ED20...`；
- 让低层 mask 复用普通 renderer last-code：test8 整页重复“息”；
- 整个 Hell/WAZ 目录全部 loose 覆盖：功能可见但冗余，最终用户二进制对比收缩到 9 个真实差异；
- 把“脚本源 count”和“value object byte_count”视为同一个概念：v1.0.2/v1.0.3 导致 Backlog 扩张文本截断；
- 把八木泽名片崩溃归因于紧随其后的 #50 长度差：v1.0.3 真实 EIP/glyph failure 证伪；
- GBK glyph 失败后返回 NULL 走原版 CP932：第一次 v1.0.3 崩溃显示 EDI=0xFFFFFFFF，必须禁止。

## 11. 崩溃诊断

VEH 只记录不拦截，最终 `EXCEPTION_CONTINUE_SEARCH`。保留最近 128 次脚本事件、12 个对象现场、64 个 glyph/DBCS 事件、寄存器/栈/机器码/模块 RVA。EnableLog=0 时这些信息不会写文件，因此调试必须开日志。

## 12. 构建/验证

正式构建：Win32/x86 Clang + `embedded_assets.S`，无 CRT、无静态 Import Directory。运行：`build.bat`。无 clean EXE 时：`python tools\verify_release_package.py`；有固定 clean EXE 时再运行 `python tools\verify_static.py <BaldrForce.exe>`。

发行前还要生成 `文件校验.sha256` 并逐项验证。BAT 必须 UTF-8 + CRLF，`chcp 65001 >nul`。
