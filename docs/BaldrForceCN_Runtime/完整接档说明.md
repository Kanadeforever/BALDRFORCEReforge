## 2. 项目目标

用 **clean 2003 EXE + 运行时 ASI** 重建旧 46MB 汉化版的全部中文显示，不再依赖那个加壳 EXE 运行。三条工作原则：

- 只复刻**已确认的旧汉化真值**。资源差异用用户逐文件二进制对比确认，不靠「扫描中文字符」猜测。
- 不猜格式。CPU/WAZ/GRP/DAT 的内部结构不解析、不重编码，原字节进、原字节出。
- 任何超出实机证据的推断必须标成待确认；没有实机日志支持的根因结论不作为修复依据。

### 4.2 脚本 opcode 0x0B：对象布局与双长度语义

34,184 条 BFET 源字符串都能对应到脚本中的 opcode `0x0B` 字符串对象。Hook 位于 clean `0x004ACC20`，对象布局：

```text
dest-8       = value type，正常为 0x0000000B
dest-4       = 运行时字符串 byte_count（包含 NUL）
dest         = 字符缓冲区
state+0x114  = 脚本源读取游标
state+0x0C   = 当前脚本上限
state+0x128  = 当前脚本 body
```

**正确语义（v1.0.4 起）——两个长度必须分离：**

```text
state+0x114    脚本源游标：按原日文 count 前进
               作用：保证下一条 opcode 的源位置不偏移
dest-4         运行时 value object byte_count：写中文实际 GBK 长度 + NUL
               作用：保证 Backlog / 历史记录 / 二次复制看到完整中文
dest           写中文原始 GBK + NUL
```

Hook 命中 BFET 或 `after.bin` direct-entry 时的执行顺序：
1. 先验证 `count <= limit-cur`，防止 Hook 自己越过脚本 body；
2. 脚本游标按**原 count** 前进（`*(DWORD*)(state+0x114)=cur+count`）；
3. 中文 GBK 写到 `dest` 并补 NUL；
4. `*(DWORD*)(dest-4)` 更新为中文长度 + 1；
5. 注册 GBK provenance/range；
6. 诊断事件同时保存原 count 与更新后的 value_count。

未命中翻译时按原 count 原样复制，不改内容。

**决定性证据**：`jyosyo05.bin #64` 的 `「………什么……」`——日文 20 bytes、中文 26 bytes、原脚本 `count=21`。v1.0.3 主显示已把 26 个 GBK 字节写进对象，但 `dest-4` 仍是 21，用户看到末尾缺符号/方块，随后打开 Backlog 崩溃；该长度差会正好切在 GBK 双字节中间。v1.0.4 中该句源 count 仍为 21，运行时对象 byte_count 变为 27。

**全量长度统计（34,184 条）**：3,909 等长、29,633 中文更短、642 中文更长。若某个二次消费者绕过 value object、直接拿源 count 截译文，642 条扩张文本中有 627 条会切进 GBK 双字节；另有 1 条中文自身 `「/」` 数量不平衡、6 条中日引号数量发生变化。因此 #64 末端缺符号优先判断为运行时截断，而不是普遍性翻译漏符号。

### 4.3 低层 1bpp 字形链（test8 → test11，已冻结）

普通菜单/剧情走全局 DBCS/GDI renderer；Information / 阅览信息与 TORU 练习招式列表另外经过两处原版 1bpp blitter（`0x00415840`、`0x00415CF1`）。旧汉化把这里的 `mov esi,[ebp+8Ch]` 换成 `call .zeas 0x007DC1A0`，由 `.zeas` 读「当前低层字符」、用 GDI 生成 1bpp mask、把 mask 指针放回 `ESI` 给原 blitter。这条链必须同时成立：资源内容正确 → 字节按 GBK 两字节分组 → 当前字符同步到低层专用状态 → GDI 生成正确 1bpp mask → 原 blitter 消费 mask。任何一层错误都会产生不同形态的乱码。

证据链：

| 阶段 | 现象 | 结论 |
|---|---|---|
| test8 | 日志 `[HIT] old-localization low-level 1bpp glyph mask active, code=0x0000CFA2, rowstride=4`；整页大量重复「息」 | DAT/WAZ 已进引擎、mask 路径能跑，但低层把普通 renderer 的 `g_renderer_last_code` 当当前字符，一个旧 code 被反复复用 |
| — | 旧汉化存在独立状态 `0x007DDFF0`（当前低层字符 code），由 `0x004155B0` / `0x00415710` 两个 lookup 函数更新，再由 `.zeas` 读取 | 普通 renderer 状态与这条 1bpp 状态不可混用 |
| test9 | `[WARN] low-level glyph-code lookup signatures DBCS/single=0/0`，逐字乱码 | 签名误用了旧汉化绝对表地址 `0x005340xx`，两个 Hook 根本没装上；mask 安全回退到原日文字库。不是「同步后仍失败」 |
| test10 | Hook 装上了（`@ 0x004155B0 / 0x00415710`），画面变成大量 `?`。TRACE：`CF / E0C2 / ED20 / CD / B8`（分隔符代表分组边界） | lookup 入口捕获忠实记录参数，但参数在进入 lookup **之前**已被 clean Shift-JIS tokenizer 拆错。改 mask 或 lookup 入口都解决不了根因 |
| test11 | 五点补丁 + 两个 mask Hook 后实机通过 | 见下 |

旧汉化正确文本「相马透」的 GBK 是 `CF E0 C2 ED CD B8`，正确 WORD 应为 `CFE0 | C2ED | CDB8`。

**test11 复刻的五点（`install_lowlevel_oldlocalization_patches()`）**：

| VA | clean | 落地语义 |
|---|---|---|
| `0x004154AD` | `3C A0` | `3C FF`：前面已 `test al,80h`，于是 `0x80..0xFE` 全部进 DBCS，与普通 renderer 的旧汉化全局规则一致 |
| `0x00415B2D` | `3C A0` | 同上 |
| `0x004170BF` | `3C A0` | 同上 |
| `0x004155E2` | 16 字节 clean SJIS 区间逻辑 | 等价 `and eax,0000FFFFh; mov [current_code],eax; nop; mov eax,0`，把 DBCS WORD 存进 `g_lowlevel_current_code` |
| `0x0041572D` | 9 字节 clean single 上界逻辑 | 等价 `movzx eax,al; mov [current_code],eax; nop` |

**安全策略**：安装前一次性验证以上五处的 clean 原字节，任意一处不符则**一处都不写**，只打印：

```text
[WARN] low-level old-localization patch validation failed; no routing/state bytes were changed.
```

因此不会出现「只改了 caller、没改 state」这种版本偏差。旧汉化原版的状态地址是 `0x007DDFF0`，test11 起改为 ASI 内的 `g_lowlevel_current_code`。

**验收标准（已由实机升级为事实）**：启动日志必须出现

```text
[OK] old-localization low-level DBCS routing patches @ 0x004154AD / 0x00415B2D / 0x004170BF
[OK] old-localization glyph lookup state patches @ 0x004155E2 / 0x0041572D
[OK] old-localization low-level glyph-mask hooks @ 0x00415840 / 0x00415CF1
```

Information 第一组中文最有价值的 TRACE 是 `CFE0 / C2ED / CDB8`；TORU 练习「轻拳」应包含 `C7E1 / C8AD`。若 WORD 已正确而画面仍错，才进入 1bpp mask 的 bitmap/stride/height 最后一层；若 WORD 仍错，则继续追 caller，而不是改资源或字体。

用户在 2026-09-20 实机确认：Information / 阅览信息与 TORU 练习招式列表已完整恢复正确中文，test8 的重复「息」、test9 的逐字 mojibake、test10 的大量问号均不再出现。这五点补丁 + 两个 mask Hook 自此为稳定基线。

### 4.4 普通 GBK renderer 与取字失败策略

全局 renderer 的关键 Hook 见 4.1（`0x00489726 / 0x00489852 / 0x00489897`）。旧汉化规则已实机确认：lead byte `0x80..0xFE` 全部按双字节消费，源码中即 `if(a<0x80||a>0xFE)return 0;`。

v1.0.3 第一次崩溃现场：

```text
ExceptionCode  = 0xC0000005
EIP            = 0x0048A974
访问类型       = 读取
目标地址       = 0xFFFFFFFF（EDI=0xFFFFFFFF）
最近脚本       = jyosyo05.bin #49，71->71
renderer_hits  = 1290
glyph_builds   = 390
glyph_failures = 1
```

`0x0048A974` 的故障指令在原 renderer 内使用字形指针，结合唯一一次 glyph failure，收敛为：**已经按 GBK 分类的字符在 GDI ANSI 取字失败后回到了原 CP932 字形路径**，把无效字形指针（`0xFFFFFFFF`）带进原渲染器。

v1.0.4 的安全策略（普通 renderer 与低层 1bpp mask 共用同一规则）：

1. 默认仍优先 `GetGlyphOutlineA` + GB2312，最大限度保持 v1.0.1 已通过的视觉；
2. ANSI 失败时把 GBK bytes 按 CP936 转 Unicode；
3. 用 `GetGlyphOutlineW` 重取；
4. 若两条 GDI 路径都失败，返回合法全 0 字形/掩码缓冲；
5. 已确认 GBK 的字符**绝不**再因为缺字返回 NULL 去走 CP932 fallback。

用户配置了 `FontFace` 时，GBK 字形直接优先使用 Unicode 字体 DC，避免字体名受系统 ANSI 代码页影响。

## 7. 运行架构

```text
BaldrForce.exe 加载 BaldrForceCN.asi
  -> InitializeASI 导出被调用
     -> 解析 INI（GetPrivateProfileStringW，运行时解析，不产生静态导入）
     -> 打开 BaldrForceCN.log（UTF-8 BOM，位于 ASI 同目录）
     -> 注册增强 VEH
     -> 安装 DAT overlay Hook（0x004A9D40）
     -> 安装全局 DBCS/GDI renderer Hook（0x00489726/0x00489852/0x00489897）
     -> 安装静态文本补丁（legacy / UI / encoding-normalization / late）
     -> 安装低层 DBCS routing + glyph-state + 1bpp mask Hook
     -> 安装 opcode 0x0B 脚本复制 Hook（0x004ACC20）
     -> IAT Hook：CreateFileA / MultiByteToWideChar / WideCharToMultiByte /
        CreateFontIndirectW / lstrcpyA / lstrcatA / wvsprintfA / wsprintfA
```

资源路径处理：游戏 `CreateFileA` 命中 9 个白名单路径时，ASI 在自身目录创建隐藏、`FILE_FLAG_DELETE_ON_CLOSE` 的真实 backing file，写入内嵌旧汉化原字节，文件指针归零，返回**真实 Windows HANDLE**。游戏后续 `GetFileSize / ReadFile / SetFilePointer / CloseHandle` 全部由 Windows 正常处理，不伪造句柄；句柄关闭时临时文件自动删除。其它路径完全不拦截。

日志：`BaldrForceCN.log`，紧随 ASI 目录定位，每次启动覆盖，UTF-8 BOM。等级前缀固定为 `[信息] / [成功] / [警告] / [失败] / [命中] / [追踪] / [诊断]`；技术标识（BFET、GBK、DBCS、IAT、Hook、API 名、路径、地址、十六进制值）保留原文。

增强 VEH（只记录，不拦截）：只处理 Access Violation、In-page Error、Illegal Instruction、整数除零/溢出、Stack Overflow，最后始终 `EXCEPTION_CONTINUE_SEARCH`，不改 EIP、不吞异常；日志末尾主动 `FlushFileBuffers`。一次崩溃尽量保存：

- ExceptionAddress/EIP 与模块 RVA，以及 `VirtualQuery AllocationBase + 模块 RVA`（异常落在其它映像时可直接定位）；
- 异常参数、EAX~EDI/EBP/ESP/EFlags/段寄存器、EIP 附近机器码、故障目标与寄存器指向内存；
- 32 个栈 DWORD、前 64 个栈 DWORD 中的代码候选、最多 16 层 EBP frame；
- 最近 **128** 次脚本复制事件（含文件名、mapping #、state/body/limit/post_cur、value type/count、日/中 hash/长度、前 32 字节原始预览）；
- 最近 **12** 个仍可读 value object、最近 **64** 次 DBCS/字形事件；
- renderer/glyph/mask/DAT/资源计数，字形失败计数 `ansi_outline_failures / unicode_fallbacks / hard_outline_failures`。

字形 fallback 诊断文案：

```text
[诊断] ANSI 中文字形失败后已由 Unicode fallback 恢复，GBK字符码=...，字号=...
[警告] GBK 字形的 ANSI/Unicode 两条 GDI 路径均失败；将返回安全空白字形而不回退 CP932...
```

## 8. 使用与配置

发行包四个文件放在**游戏主 EXE 目录**（正常发行直接同目录即可）：`BaldrForceCN.asi`、`BaldrForceCN.ini`、`Update.pac`、`Chapter.pac`。日志和 INI 都按 ASI 自身目录定位。已不再需要 `BaldrForceCN_data`。

`BaldrForceCN.ini` 必须与 ASI 同目录；文件不存在时程序使用默认值，不影响汉化加载。本版**故意只开放两个安全选项**：

```ini
[BaldrForceCN]
FontFace=
EnableLog=1
```

**FontFace**
留空即保持已实机验证的默认规则：小字号按宋体方向、大字号按黑体方向，不会因为重新加入 INI 而改变 v1.0.1 的默认视觉。填 Windows 已安装字体族名（如 `Microsoft YaHei`）可换字体。随包 INI 用 **UTF-16 LE** 保存，`GetPrivateProfileStringW` 可直接读中文族名；若被第三方编辑器改成其它编码，建议改用英文字体族名以免 ANSI 代码页导致字体名乱码。自定义字体会作用到两处：游戏的 `CreateFontIndirectW` Hook，以及 Runtime 自己用于 GBK `GetGlyphOutlineW` 的字形 DC；它**不会**改变游戏贴图字体或 HELLMODE 图片资源。指定字体缺某个汉字时也不会退回 CP932，而是走 Unicode fallback / 安全空白字形。

**EnableLog**
`1`：创建 `BaldrForceCN.log`，每次启动覆盖旧日志（UTF-8 BOM，ASI 同目录）。`0`：本次运行不创建或覆盖日志；已有旧日志不会被主动删除，所以判断日志是否关闭不能只看目录里是否还有旧文件。`EnableLog=0` 只让 `log_*` 因为没有日志句柄变成 no-op，**不会**卸载 VEH 或改变游戏逻辑；排查崩溃/乱码/资源漏项必须改回 `1`。

历史版本曾出现过的 `EnableFontHook / ForceCharset / ContextBytes` 等内部参数已证明属于汉化架构的一部分，不再允许通过 INI 改动；源码中它们固定为 `g_enable_font_hook=1`、`g_enable_wctomb_hook=1`、`g_force_charset=GB2312_CHARSET`、`g_context_bytes=128`。编码、GB2312 charset、BFET、DBCS 路由、资源覆盖、Hook 地址同样没有任何 INI 开关。

**必测 B：Backlog #64**
走到 `jyosyo05.bin #64` 的 `「………什么……」`。通过标准：右侧结束符完整、不出现末尾方块；随后打开 Backlog 可正常查看、不崩溃。日志应出现类似：

```text
[诊断][Backlog复现句] ... 脚本源count仍为21，运行时value object count已更新为27。
```
