# 低层字形同步修复说明

本文记录 Information / 阅览信息与 TORU 练习招式列表这条特殊 1bpp 文本链从 test8 到 test11 的完整证据。test11 已于 2026-09-20 实机确认完全修复；v1.0.4 继续把三处 DBCS routing、两处 glyph-state 与两个 1bpp Hook 作为冻结基线。结论以旧 46MB 汉化运行时反编译、固定 clean 2003 反编译和用户实机日志共同为准。

## 1. 为什么这条文字链和普通菜单不同

普通菜单/剧情的主要中文已经能通过全局 DBCS/GDI renderer 正常显示，但 Information 和练习招式列表还会经过两处原版 1bpp blitter：

```text
0x00415840
0x00415CF1
```

旧 46MB 汉化把这里原来的：

```asm
mov esi,[ebp+8Ch]
```

替换为调用 `.zeas 0x007DC1A0`。`.zeas` 再读取“当前低层字符”，调用 GDI 生成 1bpp mask，最后把 mask 指针放回 `ESI` 给原 blitter 使用。

因此这条链必须同时满足：

```text
资源内容正确
→ 字节必须按 GBK 两字节规则分组
→ 当前字符必须同步到低层专用状态
→ GDI 生成正确 1bpp mask
→ 原 blitter 消费 mask
```

任何一层错误都会产生不同形态的乱码。

## 2. test8：mask 能画，但字符状态是陈旧的

test8 日志已经确认：

```text
[HIT] localized DAT overlay: DatabaseInfo.DAT bytes=69972
[HIT] localized WAZ redirect: tooru.waz
[HIT] old-localization low-level 1bpp glyph mask active, code=0x0000CFA2, rowstride=4
```

`CF A2` 是 GBK“息”。画面恰好出现整页大量重复“息”。

这证明：

1. DAT/WAZ 资源已经送进 clean 引擎；
2. 低层 GDI mask 构建路径能运行；
3. 但 test8 把普通 renderer 的 `g_renderer_last_code` 当成低层当前字符，导致一个旧 code 被不断复用。

## 3. 旧汉化的独立字符状态

旧 46MB 汉化运行时存在独立状态：

```text
0x007DDFF0  旧汉化当前低层字符 code
```

两个 lookup 函数会更新它：

```text
0x004155B0  DBCS glyph lookup
0x00415710  single-byte glyph lookup
```

而 `.zeas 0x007DC1A0` 再读取它，为 `0x415840 / 0x415CF1` 生成 mask。

因此普通 renderer 状态和这条 1bpp 状态不能混用。

## 4. test9：方向正确，但两个 Hook 根本没有装上

test9 增加 `g_lowlevel_current_code` 并计划从两个 lookup 入口捕获参数，但实机日志是：

```text
[WARN] low-level glyph-code lookup signatures DBCS/single=0/0
[WARN] low-level glyph-code synchronization unavailable...
```

后来确认签名误用了旧 46MB 汉化的绝对表地址 `0x005340xx`，而 fixed clean 2003 使用 `0x005350xx`。

所以 test9 的逐字乱码不是“同步后仍然失败”，而是同步根本没执行，mask 安全回退到原日文字库。

## 5. test10：同步 Hook 真正安装，但暴露了更上游的错误

test10 改成 clean 2003 正确 lookup 签名，实机日志终于出现：

```text
[OK] old-localization low-level glyph-code synchronization hooks @ 0x004155B0 / 0x00415710
[OK] old-localization low-level glyph-mask hooks @ 0x00415840 / 0x00415CF1
```

但是画面变成大量 `?`。决定性证据来自 TRACE：

```text
#1  code=0x000000CF
#2  code=0x0000E0C2
#3  code=0x0000ED20
#4  code=0x000000CD
#5  code=0x000000B8
```

旧汉化同位置角色名是“相马 透”。忽略空格，“相马透”的 GBK 是：

```text
相  CF E0
马  C2 ED
透  CD B8
```

正确 WORD 应是：

```text
CFE0 | C2ED | CDB8
```

而 test10 得到：

```text
CF | E0C2 | ED20 | CD | B8
```

这说明 lookup 入口捕获本身忠实记录了参数，但**参数在进入 lookup 之前就已经被 clean Shift-JIS tokenizer 拆错**。因此继续修改 mask 或 lookup 入口都不会解决根因。

## 6. 旧汉化真正遗漏的第一层：三个 caller 的 A0→FF

扫描旧汉化 runtime 对 `call 0x004155B0` 的所有引用，确认共有 10 个 caller；其中只有三个 caller 的 DBCS 判定被汉化组改动：

```text
0x004154AD  old: 3C FF   clean: 3C A0
0x00415B2D  old: 3C FF   clean: 3C A0
0x004170BF  old: 3C FF   clean: 3C A0
```

代表性 clean 逻辑可简化为：

```asm
mov  al,[esi]       ; 当前第一个字节
test al,80h         ; 没有高位 -> ASCII/single
je   single
cmp  al,A0h         ; Shift-JIS 半角/lead-byte 分界
jb   dbcs
cmp  al,DFh
jbe  single
```

旧汉化只把：

```asm
cmp al,A0h
```

改为：

```asm
cmp al,FFh
```

因为前面已经 `test al,80h`，所以 `0x80..0xFE` 全部满足 `< FF`，统一进入 DBCS 路径。这和项目已经在普通 renderer 验证成功的旧汉化全局 `0x80..0xFE` 双字节规则一致。

对于：

```text
CF E0 C2 ED CD B8
```

修复后的 caller 应依次组装：

```text
CFE0
C2ED
CDB8
```

## 7. 旧汉化真正遗漏的第二层：lookup 函数内部状态写入

旧汉化不是在 lookup 函数入口额外装一个 trampoline，而是直接改写函数内部指令。

### 7.1 DBCS lookup：0x004155E2

clean 2003 原字节：

```text
66 3D FD 81 73 14 25 FF FF 00 00 2D 40 81 00 00
```

对应的关键语义是继续按 Shift-JIS 字区判断/计算。

旧汉化把这 16 字节改成等价于：

```asm
and eax,0000FFFFh
mov [current_code],eax
nop
mov eax,0
```

旧版 `current_code` 是 `0x007DDFF0`；test11 把 `A3` 的绝对地址改成 ASI 内的 `g_lowlevel_current_code`。

### 7.2 single lookup：0x0041572D

clean 原字节：

```text
3C 7F 77 12 25 FF 00 00 00
```

旧汉化等价改成：

```asm
movzx eax,al
mov [current_code],eax
nop
```

test11 同样把状态地址指向 `g_lowlevel_current_code`。

## 8. test11 的五点原样复刻

本版只新增以下五处 old-localization-equivalent patch：

| VA | clean | test11/旧汉化语义 |
|---|---|---|
| `0x004154AD` | `3C A0` | `3C FF`，低层 caller 使用 0x80..0xFE 双字节路由 |
| `0x00415B2D` | `3C A0` | `3C FF` |
| `0x004170BF` | `3C A0` | `3C FF` |
| `0x004155E2` | 16-byte clean SJIS 区间逻辑 | 保存 DBCS WORD 到低层专用状态 |
| `0x0041572D` | 9-byte clean single 上界逻辑 | 保存 single BYTE 到低层专用状态 |

然后继续使用已经确认的：

```text
0x00415840  1bpp mask blitter A Hook
0x00415CF1  1bpp mask blitter B Hook
```

## 9. 安全策略

`install_lowlevel_oldlocalization_patches()` 会先一次性验证全部五处 clean 原字节。任意一处不符：

```text
[WARN] low-level old-localization patch validation failed; no routing/state bytes were changed.
```

并打印五处实际字节。

只有全部匹配后才会执行任何写入。因此不会出现“只改了 caller、没改 state”或“只改了 state、没改 caller”的正常版本偏差。

## 10. test11 验收标准

启动时必须出现：

```text
[OK] old-localization low-level DBCS routing patches @ 0x004154AD / 0x00415B2D / 0x004170BF
[OK] old-localization glyph lookup state patches @ 0x004155E2 / 0x0041572D
[OK] old-localization low-level glyph-mask hooks @ 0x00415840 / 0x00415CF1
```

Information 第一组中文最有价值的 TRACE 是：

```text
CFE0
C2ED
CDB8
```

TORU 练习“轻拳”应包含：

```text
C7E1
C8AD
```

如果这些 WORD 已正确，而画面仍然错，才进入 1bpp mask 的 bitmap/stride/height 最后层；如果 WORD 仍错误，则继续追 caller，而不是改资源或字体。

## 11. 已冻结事项

- DAT overlay 不改；test10 已证明 `DatabaseInfo.DAT` 正常命中。
- `TOORU.WAZ` 不改；它是旧汉化 VFS 的确认 GBK 资源。
- 普通 2bpp renderer 不改；gbk7 仍是已通过基线。
- `戻る` 不翻译；旧 46MB 汉化同样保持日文。
- test5/test6 的 glyph 坐标实验已证伪，不重复。

## 12. test11 实机最终结论与 test12 冻结策略

用户在 2026-09-20 实机确认：

- Information / 阅览信息已完整恢复正确中文；
- TORU 练习模式招式列表已完整恢复正确中文；
- 不再出现 test8 的重复“息”、test9 的逐字 mojibake、test10 的大量问号。

因此本文件前面的“test11 验收标准”已经从待验证条件升级为**已通过事实**。test11 的五点 old-localization patch + 两个低层 mask Hook 正式成为稳定基线。

`v0.2-test12-assets1` 不修改这些地址、代码模板或 mask 逻辑。本轮只做资源层补漏与打包收敛：把 `TOORU.WAZ` 和 `Bmp\Hell` 资源并入 ASI，并取消 INI。

后续只有出现明确回归证据时，才允许重新打开这条低层字体链；普通漏图/漏资源不应再通过修改 DBCS routing 或 glyph mask 解决。

## v1.0.4-crashfix1：普通/低层取字失败的安全回退

v1.0.3 第一次崩溃日志第一次给出 `glyph_failures=1 + EIP=0x0048A974 + EDI=0xFFFFFFFF`。本版没有修改 test11 已通过的低层地址或字节路由；只统一修改“GDI 取不到某个已经确认的 GBK 字符时怎么办”：默认 `GetGlyphOutlineA` 失败后按 CP936 转 Unicode 并调用 `GetGlyphOutlineW`；两条都失败时返回合法空白缓冲，不再回原版 CP932。低层 1bpp mask 同样使用这一规则。

这属于**失败路径加固**，不是重新设计 test11 字形同步。若本版 Information/TORU 回归，应首先检查这次 fallback 实现，而不要撤销 `0x4154AD / 0x415B2D / 0x4170BF / 0x4155E2 / 0x41572D / 0x415840 / 0x415CF1` 的已确认方案。
