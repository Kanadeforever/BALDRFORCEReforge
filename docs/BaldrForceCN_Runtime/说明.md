# BaldrForceCN Runtime v1.0.4-crashfix1

这是 BALDR FORCE 2003 clean EXE 汉化运行时的**双崩溃修复测试版**。它以 v1.0.1 已实机通过的中文覆盖、Information/TORU、HELLMODE、DAT/WAZ 和 9 个差异资源为基础，并根据 v1.0.3-crashdiag2 返回的两份完整异常日志修复两个彼此独立的问题。

## 本版修复的两个根因

第一类是“八木泽递名片”后立即崩溃。`第一次.log` 捕获到主程序 `EIP=0x0048A974`、读取 `0xFFFFFFFF`，同时运行计数出现 `glyph_failures=1`。该地址位于普通文字 renderer 的字形位图消费路径；这说明某个已经识别为 GBK 的字符在 `GetGlyphOutlineA` 失败后掉回原版 CP932 路径，最终把无效字形指针带到原渲染器。本版改为：默认仍优先走已经实机通过的 ANSI/GB2312 字形路径；失败时把 GBK 两字节按 CP936 转 Unicode，再用 `GetGlyphOutlineW` 取字；若两条 GDI 路径都失败，也返回合法的空白字形，不再把确认过的 GBK 字符退回 CP932。

第二类是 `jyosyo05.bin #64` 的 `「………什么……」` 末尾缺符号/方块，随后打开 Backlog 崩溃。`第二次.log` 明确记录这条映射为 JA 20 bytes -> ZH 26 bytes、原脚本 `count=21`。v1.0.3 把中文写进运行时对象，却仍让 `dest-4 byte_count=21`，Backlog 等二次消费者因此按旧长度截断，恰好切在 GBK 双字节中间。本版正式分离两个长度：

```text
脚本源游标 state+0x114
    始终按原日文 count 前进
    作用：保证下一条 opcode 的源位置不偏移

运行时 value object 的 dest-4 byte_count
    改为实际中文 GBK 长度 + NUL
    作用：保证 Backlog/历史记录/二次复制看到完整中文
```

因此 #64 的源 `count` 仍是 21，但运行时对象 `byte_count` 会变成 27。

## 可选 INI

`BaldrForceCN.ini` 从本版恢复，但**只提供两个安全选项**：

```ini
[BaldrForceCN]
FontFace=
EnableLog=1
```

`FontFace=` 留空就是此前实机通过的默认宋体/黑体规则；填写字体族名称后，普通字体 Hook 和 Runtime 自己的 GBK 字形生成器都会使用该字体。中文字体名建议保持本文件为 UTF-16 LE；也可以使用 `Microsoft YaHei` 之类英文族名。

`EnableLog=1` 写 `BaldrForceCN.log`；设为 `0` 后本次启动不创建/覆盖日志。排查问题时请保持 `1`。

编码、GB2312 charset、BFET、DBCS 路由、资源覆盖、Hook 地址等关键行为**没有任何 INI 开关**，仍固定在代码里。

## release 文件

```text
BaldrForceCN.asi
BaldrForceCN.ini
Update.pac
Chapter.pac
```

`Update.pac / Chapter.pac` 仍放在游戏主 EXE 目录；正常发行包四个文件直接放同一目录即可。日志和 INI 都按 `BaldrForceCN.asi` 自身目录定位。

## 本轮优先实机验证

1. 只加载 CN ASI，复现八木泽递名片：应该能够越过原来的 `0x0048A974` 崩溃点。若 ANSI 取字确实失败并被救回，日志会出现 `ANSI 中文字形失败后已由 Unicode fallback 恢复`。
2. 到 `jyosyo05.bin #64`：画面应完整显示 `「………什么……」`，末尾不再出现方块；随后打开 Backlog 不应崩溃。
3. 回归检查 Information、TORU 练习招式、HELLMODE 图片，确认 v1.0.1 已通过内容没有回归。
4. 如仍有崩溃，完整返回 `BaldrForceCN.log`。增强 VEH 仍保留，不会吞异常。
